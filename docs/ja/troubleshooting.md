# トラブルシューティング

> 英語版: [../troubleshooting.md](../troubleshooting.md)

症状ベースで、よくあるものから順に並べています。迷ったときは、API ログと `http://localhost:8791/api/v1/health` が最速の診断手段です。

## スコアと判定

**セットアップ直後にすべての画像が高スコアになる(すべて NG)**
バンクが小さすぎるか、正常のばらつきをまだカバーできていません。ロット差・照明の揺らぎ・位置ずれの幅を含む良品画像を追加で教えてから、分離度評価を再実行してください。

**特定の無害なパターンが繰り返し反応する**
そのパターンの例を 1 枚 **negative** 層に教えてください。次の画像から、その近傍の反応が抑制されます。あるいは、そのパターンを含む良品画像を追加で教える方法もあります。

**分離度評価で OK と NG の分布が重なる**
- NG 画像に欠陥矩形をマークしてください(見本が α 項を鋭くします)。
- 射影マップでラベル間違いの教示がないか確認してください(NG クラスタの中に入り込んでいる「OK」画像は、たいていラベル付けミスです)。
- 非常に微細な欠陥は、特徴解像度で分離できる下限を下回っていることがあります — 検査対象領域をより狭くカメラでクロップしてみてください。

**更新や設定変更の後にスコアがわずかにずれた**
圧縮設定はスコア定義の一部です。int8 / IVF を切り替えると、キャッシュ済みの評価は再計算され、保存済みの判定レシピには「要再確認」の警告が付きます — 分離度評価を再実行して保存し直してください。圧縮自体による分布のずれは、検証したプロジェクトでは判定に影響しませんでした。

**教示後の最初の採点が遅い**
想定どおりの挙動です: バンク変更後に一度だけ、圧縮済みバンクのテンソル(場合によってはルーティングインデックスも)が再構築されます。2 回目以降の採点は高速です。非常に大きなバンクでは、この 1 回限りの処理に数秒かかることがあります。

## 教示

**ラベルを付け直したのに検査が変わらない**
ラベルはラベルセットにあり、バンクはそこから作られます。バンクタブのステップ③で**バンクを組み立てる**を押してください — ラベルを変えるとこのステップの ✓ は外れます。それがバンクとラベルがずれている合図です。

**巨大な画像で教示が固まったように見える**
非常に大きな画像(スマートフォン写真、つなぎ合わせたラインスキャン)は何千ものパッチを抽出します。画像 1 枚あたりの上限(既定 2048)で保存量は抑えられますが、抽出自体は画像全体を処理します。検査対象領域をカメラでクロップした画像の使用をおすすめします。

**「bank is at capacity」**
選択中の容量プランが満杯です。設定で容量プランを引き上げる(小 → 中 → 大)か、不要になった教示済み画像を削除してください(画像単位の削除は、その画像が寄与した行だけを正確に除去します)。

**サーバーの RAM が数十 GB に達する / プロジェクトを開くとマシンがページングする**
ほぼすべてのケースで原因は、これらの層に 1 枚あたりのパッチ上限が導入される前に NG(critical / negative)画像を教えたバンクです — フル解像度の NG 画像 1 枚が 100k+ パッチを寄与することがあり、当時の設定のゲージは normal 層しか表示していませんでした。設定を確認してください: 容量バーの下の行にラベル付きパッチ数が表示されます。該当するバンクは次のコマンドでその場で縮小できます

```
python scripts/reduce_bank.py --projects-dir <your projects dir>          # dry run
python scripts/reduce_bank.py --projects-dir <your projects dir> --apply  # writes, backs up first
```

欠陥マークはすべて縮小後も保持されます。新規の教示は全層で上限が適用されるため、これは 1 回限りのクリーンアップであり、継続的なメンテナンスではありません。

## サーバーと UI

**「中止」(Cancel)を押しても何も起きていないように見える**
現行ビルドでは、中止は実行中のリクエストを即座に中断し、ボタンはクリックを受け付けたことを表示し(「cancelling…」)、中止された検査は表示もログ記録もされません。中止が無視されているように見える場合は、フラグがリクエストの合間にしか読まれない 0.1.0 より前のビルドを実行しています — 更新してください。

**タブに「no active project」と表示される / 409 が繰り返し発生する**
別のクライアント(またはサーバー再起動)がアクティブなバンクの束縛を解除しました。開いているタブは数秒以内に自動で再選択します。再選択されない場合は、プロジェクトを選び直してください。バンク切り替えと競合した書き込みは設計どおり 409 で失敗します — タブが再束縛された後に再試行してください。

**プロジェクトを開くと「corrupt bank」(422)になる**
メタデータのサイドカーが特徴ファイルと食い違っています(典型的にはハードクラッシュの後)。回復可能なケースはロード時にサーバーが自動修復します(影響を受けたラベルの重症度マークは既定値にリセットされます)。normal の `bank.npy` 自体が読めない場合はバックアップから復元してください — 書き込みはアトミックなので、これはストレージレベルの損傷を示します。

**UI は読み込まれるがすべて 404 になる / ページが古い**
ハードリロード(Ctrl+F5)してください。自前ビルドの場合は、UI を再ビルドし(`apps/ui` で `npm run build`)、サーバーを再起動したか確認してください。

## GPU

**GPU が使われない(デバイスが cpu と表示される)**
設定 → ハードウェアで CUDA デバイスを選択してください。何も表示されない場合は、インストールされている PyTorch が CPU 専用です — `cuda` 引数を付けてインストーラーを再実行してください。

**採点時に CUDA がメモリ不足(out-of-memory)になる**
大きなバンク + 小さな GPU の組み合わせです: より小さなバンク容量プランを選ぶか、圧縮を有効のままにしてください(int8 で常駐バンクは半減します)。採点は空き VRAM に収まるよう自動でチャンク分割されるため、OOM は通常、別のプロセスがメモリを掴んでいることを示します — アプリ内の GPU パネルを確認してください。

**Windows で `nvidia-smi` のメモリ使用量が巨大に見える**
WDDM は割り当て済みではなく予約済みのメモリを報告します。アプリ内のヘルスパネル(`torch.cuda.memory_allocated`)を信頼してください。

## ログの場所

- API ログ: `uvicorn` プロセスのコンソール / リダイレクト先ファイル(同梱の Windows タスクスクリプト使用時は `_api_task.log`)。
- 各 API レスポンスにはリクエスト ID が付き、サーバーログの行にも同じ ID が含まれます。
- `GET /api/v1/health` — バージョン、ディスク、RAM、GPU 割り当て。
